通知推送接入说明

宿主接管系统推送注册，技威 SDK 负责解析、展示与点击跳转。这是本 demo 的推送接入边界， 也是本 demo 固定的接入边界。

1. 边界：谁负责什么

Section titled “1. 边界：谁负责什么”
事项 负责方
申请通知权限 宿主 App
获取系统推送标识（Android FCM token / iOS APNs token） 宿主 App
把标识上报技威云（uploadPushToken） 宿主 App
接收推送消息 宿主 App
把推送原始数据交给 SDK（receivePushNotification / clickPushNotification） 宿主 App
解析推送内容 技威 SDK
展示通知、点击后跳转页面 技威 SDK

宿主把 SDK 初始化参数 disablePushNotification 传 true，SDK 内置的 FCM 服务就不再注册。 它关掉的只是「注册与接收」，不是 SDK 的推送处理能力——转交之后 SDK 照常发通知、照常跳转。 如果宿主自己再发一条通知，同一条推送会弹两次。

2. iOS 的两条通道

Section titled “2. iOS 的两条通道”

技威云在 iOS 上只认 APNs token。接 FCM 的客户仍然要把 APNs token 报上去，FCM 只是换了一条 「谁注册、谁收消息」的路。demo 因此提供两条可切换的通道，默认 APNs 直连：

通道 谁注册 上报的标识 适合谁
APNs 直连 宿主 AppDelegate APNs token 只想用系统推送、依赖最少的客户
FCM firebase_messaging APNs token（FCM token 只做诊断） 统一接 FCM 的客户

通道在开发者页切换，改完必须重启 App。Android 没有这个开关：只有 FCM 一条路。

pubspec.yaml 里只要引了 firebase_messaging，iOS 上 Firebase Pods 就会始终被链接，运行期开关 摘不掉它。真实客户如果只用 APNs，不要引这个依赖即可，而不是在 Podfile 里做条件化。

3. 配置清单

Section titled “3. 配置清单”

3.1 Firebase 控制台

Section titled “3.1 Firebase 控制台”
  • 建好项目后新增 Android 应用，包名 com.gwell.demo.develop，下载 google-services.json 放到 android/app/。
  • 新增 iOS 应用，Bundle ID com.yoosee.developer.demo，下载 GoogleService-Info.plist 放到 ios/Runner/，并在 Xcode 里加入 Runner target（Add to target）。
  • 在 Firebase 控制台 → 项目设置 → 服务账号里生成 FCM 发送用的服务账号 JSON，交给技威云后台配置。

两个配置文件都提交进本仓库（Firebase 的 API key 按官方说明不是机密），真实宿主必须换成自己项目的文件。

3.2 Apple 开发者后台

Section titled “3.2 Apple 开发者后台”
  • 给 App ID com.yoosee.developer.demo 打开 Push Notifications 能力。
  • 打开 Background Modes → Remote notifications（Info.plist 里的 remote-notification 已就位）。
  • 确认 ios/Runner/Runner.entitlements 已由 CODE_SIGN_ENTITLEMENTS 挂到 Runner target （仓库里已经配好，Debug/Release/Profile 三个配置都有）。缺这一项时 registerForRemoteNotifications 会以 Code=3000 未找到应用程序的 aps-environment 的授权字符串 失败，表现就是「权限弹窗点了允许、但永远拿不到 APNs token」。
  • 在 Keys 里创建一枚 APNs Auth Key（.p8），记下 Key ID 与 Team ID，交给技威云后台配置。 .p8 只放本机，已在 .gitignore 里排除。

模拟器上永远拿不到 APNs token，必须在真机验证。开发者页的「注册异常」一行会把失败原因直接显示 出来，不用再去翻 Xcode 日志。

3.3 技威云后台

Section titled “3.3 技威云后台”
  • 提交 Android 的 google-services.json。
  • 提交 iOS 的 APNs Auth Key（.p8 + Key ID + Team ID）。

这两项只有项目方能做，demo 不代做；缺任一项的表现是「token 上报成功但收不到推送」。

4. 代码结构

Section titled “4. 代码结构”

原生侧：

  • iOS ios/Runner/AppDelegate.swift 里的 PushBridge：只做「转交 token 与 payload + 转权限请求」， 不解析、不展示、不跳转。走 FCM 时它不接管 UNUserNotificationCenter 的代理（那个代理归 firebase_messaging，两边同时设会互相顶掉）。
  • Android MainActivity.kt 与 DemoApplication.kt：只做「建通知渠道 + 发本地测试通知」。 Android 的消息接收完全在 Dart 侧，不需要宿主写 FirebaseMessagingService。

5. 后台与杀进程

Section titled “5. 后台与杀进程”

disablePushNotification = true 之后，后台推送由 firebase_messaging 的后台回调接住，在另一个 Dart isolate里转交 SDK。杀进程时那个 isolate 里 SDK 还没初始化，因此代码里先补一次 GWIoT.initialize（SDK 对重复初始化是幂等的）并等 SDK 就绪再转交，最长等 20 秒，超时放弃这次推送、 不重试。

排查顺序：先用开发者页的「喂一条模拟推送」确认 Dart → SDK → 通知栏 → 点击跳转这条链路是通的， 再去 Firebase 控制台发真实推送。这样能把「配置问题」和「链路问题」分开。

5.1 每次启动都要注册

Section titled “5.1 每次启动都要注册”

APNs 只在调用过 registerForRemoteNotifications 之后才回调 device token，而且 token 会变。 因此 APNs 通道在启动时就注册一次（activate），授权通过后再注册一次（requestPermission）， 不是「申请过权限就不再注册」。这一条与权限申请是两件事，别合并。

6. token 上报时机

Section titled “6. token 上报时机”
  • 拿到或刷新 token 时上报一次；启动拿到就调，未登录时的失败是预期——SDK 会缓存 token，登录后 自动补传（延迟 2 秒，内部还有 5 秒防抖与同 token 去重）。
  • 登录成功与登出都不要额外调一次：多调可能撞上单端登录的 clearOtherTerm 逻辑，把其他端的 token 清掉，表现为「别的手机收不到推送」。
  • 通知权限在登录成功后申请一次，冷启动不弹、用户拒绝后不重复弹。

7. 真机验收步骤

Section titled “7. 真机验收步骤”

Android：

  1. 把真实 google-services.json 放进 android/app/ 后 flutter run。
  2. 登录账号 → 允许通知权限 → 开发者页确认「上报标识」非空、「最近上报」为成功。
  3. 开发者页点「发测试通知」：应看到通知栏出现一条带自定义小图标的通知（验证渠道与图标）。
  4. 开发者页点「喂一条模拟推送」：应由 SDK 弹出通知（验证转交链路）。
  5. 在 Firebase 控制台给该设备发一条测试消息，或在技威云触发一条真实设备告警：应收到推送。
  6. 杀掉 App 后再发一条：应仍能收到（验证后台 isolate 路径）。
  7. 点击通知：应跳到 SDK 对应的页面。

iOS：

  1. 把真实 GoogleService-Info.plist 放进 ios/Runner/ 并在 Xcode 里加入 Runner target。
  2. 开发者页确认通道为「APNs 直连」（默认），登录并允许通知权限。
  3. 重复上面第 2~7 步。
  4. 切到「FCM」通道并重启 App，重复第 2~7 步：此时上报的仍应是 APNs token， 开发者页的「诊断标识」才显示 FCM token。
