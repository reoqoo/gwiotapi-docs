Feature and responsibility boundary

This page describes what the GWIoT SDK builds in, and what the customer app has to implement or can customize.

Feature boundary diagram

Section titled “Feature boundary diagram”

  • The left side is what the app implements: account management, the device list, features customized through SDK interfaces, and other business features.
  • The right side is the complete set of features the SDK builds in: scanning to bind and share devices, the device binding flow, the device feature plugin, device sharing management and the device album.
  • The app integrates with and calls the SDK, and the SDK hands results and events back to the app through observable properties and listener interfaces.

What the SDK builds in

Section titled “What the SDK builds in”
Capability Description Entry points
Initialization Initialization and SDK readiness state IInitializeComponent
Account and sign-in Account registration and sign-in interfaces, without UI IAccountRegisterComponent, IAccountManagerComponent
Device list and device info Product list, device list, device details, including cache-first queries and device event subscription IDevMangerComponent
Binding and QR scanning Entering the binding page for a given product, scanning to bind, binding events IBindComponent, IQRCodeComponent
Device feature plugin The complete device features and settings UI for each product model IPluginComponent
Live view, playback and two-way talk Player connection state, video quality, two-way talk IPlayerComponent
Multi-device live view Opening the multi-device live view page IMultiLiveComponent
Device sharing Accepting a device shared by QR code, share management IDevShareComponent
Device upgrade Checking for upgrades, opening the batch upgrade page IDevCheckUpgradeComponent, IDevUpgradeComponent
Device album Opening the device album IAlbumComponent
Message center Unread count for the message center, the SDK’s built-in message center page IMessageCenterComponent
Push Handling a user tap on a push message IPushNotificationComponent
Cloud service and traffic pages The built-in cloud service page and traffic service page ICloudServiceComponent, ITrafficServiceComponent
Help and feedback The built-in help and feedback pages IHelperPageComponent
UI, language and configuration Theme, UI copy, language, environment configuration IUIConfigurationComponent

Extension points the customer app implements

Section titled “Extension points the customer app implements”

Beyond the table above, the SDK leaves a few seams. The app implements the interface, and the SDK calls it back or returns results at the right moment. They all start with IHost.

Extension point Interface What it does
Customer service registration IHostService Where the app registers the custom interfaces and services below
App account info lookup IHostAccountService Looks up the customer app’s account info by the accessId on the Gwell side
Cloud service page takeover IHostCloudService The app supplies its own cloud service page
Technical support page IHostSupportService The app supplies its own technical support page
Traffic page takeover IHostTrafficService The app supplies its own traffic page
Custom settings items IHostSettingService The app decides whether some settings items are shown — Settings / Smart Guard / guard schedule

When these seams are needed

Section titled “When these seams are needed”

Each one is a switch that lets the customer take over a single item. When you take it over, your implementation decides the behavior. When you do not, the SDK’s built-in behavior applies.

If your app… Implement
Has its own account system, and devices must be bound to its own account IHostAccountService
Has its own cloud service or traffic entitlement page and does not want users sent to SDK built-in pages IHostCloudService, IHostTrafficService
Has its own technical support page, or hides the entry and does not want users to reach the SDK’s built-in default page IHostSupportService
Wants to customize some device settings items IHostSettingService

Note: this lists only some of the interfaces for reference. For the complete interface list, and for each interface’s signature, call timing and default behavior, refer to the API reference and the interfaces of each platform SDK.

Screens at a glance

Section titled “Screens at a glance”

The screenshots below come from a real app, so you can see the boundary between app and SDK features at a glance.

All screenshots come from the Flutter demo. They preview only part of the features; for more complete information, see the API documentation and the demo.

Screens built in by the SDK

Section titled “Screens built in by the SDK”
Screen Description
Scan to bind: the SDK’s built-in scan page. The viewfinder, the flashlight and picking a code from the album all live inside the SDK. Once a QR code is read, the SDK continues the binding flow.
Nearby device discovery: while scanning, the SDK also listens for Bluetooth broadcasts and quickly finds devices waiting to be bound.
Device setup: searching, connecting and registering the device are all done by the SDK.
Device feature plugin (home page): live video, video quality, mute, two-way talk, recording and snapshots, plus entries such as cloud storage, AI Box and playback, along with the event list. The plugin lays them all out according to the device’s capabilities.
Device settings: device information, device sharing, cloud storage status and whole-device settings.
Playback: two playback pages, one for cloud storage and one for the SD card. The date strip, the timeline colored by event type and the clip lists all come from the SDK.
Multi-device live view: 2×2 live view.
Cloud service page: an introduction to cloud services, with the eligible device list and the activation entry.
Cloud service purchase page: plans, coupons and payment all complete in one built-in WebView, so the customer can configure plans and connect its own payment account.
Traffic service page: 4G data entitlements and plan entries.
Traffic plan purchase page: the same built-in flow as the cloud service purchase page; prices and discounts are issued by the server.

Screens implemented by the app

Section titled “Screens implemented by the app”
Screen Description
Sign-up, sign-in and other account features
Device list and app shell: the card list, the bottom tab bar, and the settings / playback / share entries on each device card are all implemented by the app. Tapping one opens an SDK built-in page.
Add-device entries: a device can be added in several ways, such as scanning a code or picking a product manually to bind. For the entry, the app can use the SDK’s built-in pages or implement its own. The demo provides a reference implementation for each.
Mine: entries for device upgrade, share management, the device album, traffic, cloud storage, general settings and the message center. Each one has an SDK built-in page, and some can be customized.
