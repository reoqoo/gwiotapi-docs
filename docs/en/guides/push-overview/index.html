Push overview

This page describes the two GWIoT push paths and which messages each one carries. It also covers what the app side and the customer cloud side each have to do.

Two paths

Section titled “Two paths”
Path Receives Where messages come from Good for
App push Customer app Gwell Cloud over the system push channel (APNs on iOS, FCM on Android) Letting users see alarms and device notifications promptly
Cloud webhook Customer cloud Gwell Cloud calls back an address the customer cloud provides Letting the customer’s business systems receive order, device and binding events

You can implement one path or both — it depends on where the messages need to end up.

Message families

Section titled “Message families”
Message type Meaning
ONLINE_MSG Device online / offline
EVENTALARM Device event alarm
DEVICENOTICE Device notification (offline push)
DEVICECREATEINFO Device creation information
ORDER Order status change
DEVICE Device and plan status change
Bind Binding relationship change

Who does what

Section titled “Who does what”
Role What it does
Customer app Integrates the system push channel, hands the push token to the SDK, and handles where a tapped push takes the user
Customer cloud Exposes a publicly reachable callback address, verifies the signature on Gwell Cloud’s requests, handles each message type and returns the agreed response
SDK Handles push registration and token upload, and delivers pushes and device events back to the customer app

Next steps

Section titled “Next steps”

For the client-side integration, see Push integration.

The fields, examples and signature headers for each message are in the private repo github.com/reoqoo/gwiotapi. Opening the link needs an authorized GitHub account; if you cannot open it, contact your Gwell counterpart.
