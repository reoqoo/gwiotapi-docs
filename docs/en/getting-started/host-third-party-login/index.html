宿主账号的第三方登录与登录方式管理

This page has no maintained English version yet. The Chinese version is shown instead. Use your browser's built-in translation to read it.

宿主账号体系（Supabase Auth 模拟的那个）支持用 Google 与 Apple 登录，登录后还能在「账号与安全」 页里绑定、解绑这些登录方式，更换账号邮箱，以及添加或移除「邮箱密码登录方式」。

本文是接入配置指南：代码已经在仓库里，剩下要你做的都在各家控制台。按顺序做完， 用真机跑一遍第 6 节就能验收。

1. 链路

Section titled “1. 链路”

App 只做两件事：打开系统认证窗口、等回调。没有自建网页登录页，理由是 Supabase 的 PKCE 约束 （code verifier 必须与发起流程在同一侧）。

绑定与解绑走同一套：linkIdentity / unlinkIdentity 同样打开认证窗口，结果经 onAuthStateChange 回来。

回调回到 App 之后还有两段等待——supabase_flutter 拿 code 换会话，以及云云对接加技威云——期间 界面会盖一层**「正在完成登录」提示，免得用户以为卡住了。提示在打开浏览器那一刻就盖上，所以用户 从浏览器切回来时已经在转圈；失败、成功、或超过 20 秒**没有任何回调（多半是在浏览器里放弃了）都会 自动收起。

为什么两个平台都用外部浏览器

Section titled “为什么两个平台都用外部浏览器”

supabase_flutter 的平台默认值在两个平台都是「应用内浏览器」，而它们跟不到「重定向回自定义 scheme」那一步：

  • iOS：SFSafariViewController，表现是白页 + PlatformException(Error, 'Error while launching ...')， 回调永远回不来（supabase-flutter #1174、#819，报告者明确说换成外部浏览器就没问题）。
  • Android：Custom Tabs，同样出不来。supabase_flutter 自己在 _launchAuthUrl 里只对 「Android + Google」这一种组合强制改成外部浏览器，其余组合走平台默认就会卡在 Custom Tabs 里。

因此 demo 在 hostAuthLaunchMode() 里显式返回 LaunchMode.externalApplication，两个平台都走真正的 外部浏览器——系统会把自定义 scheme 交回 App，回调才能到达。代价是用户会离开 App 去浏览器。

不要把它改回平台默认，否则会重现白页 / 回调回不来。上游已经准备把整条 OAuth 链路从 url_launcher 换成系统 web auth session（supabase-flutter #1403），那样会自动关闭并回传回调； 但截至 supabase_flutter 2.17.2 与 3.0.0-dev.6 都还没发布。

2. 前置条件

Section titled “2. 前置条件”
平台 要去的后台 要建的东西
Google Google Cloud Console（不是 Google Play 控制台） OAuth consent screen + 一个 Web application 类型的 OAuth 客户端
Apple Apple Developer（不是 App Store Connect） 带 Sign in with Apple 能力的 App ID、一个 Services ID、一个签名 Key（.p8）

两点提醒：

  • Apple 这一套需要付费的 Apple Developer Program 会员。
  • Google 与 Apple 可以分开配。只想先跑通的话，只配 Google 就够了，Apple 留到最后。

3. Supabase 控制台

Section titled “3. Supabase 控制台”

项目：agvjkfcdnrbdgsbtsldd（https://agvjkfcdnrbdgsbtsldd.supabase.co）。

3.1 URL Configuration

Section titled “3.1 URL Configuration”

进入 Authentication → URL Configuration：

字段 值
Site URL 保持你的站点地址即可（demo 用不到，只作邮件链接的兜底）
Additional Redirect URLs 增加 com.yoosee.gwiotflutterdemo://auth-callback

这个取值必须与 Dart 侧的 hostAuthRedirectUrl、Android 的 intent-filter、iOS 的 CFBundleURLTypes 逐字一致。四处任意一处不一致，表现都是「点了链接没反应」。 仓库里有一条单元测试专门守这个一致性（test/host_account_service_test.dart）。

不配这一条的后果：注册确认邮件与重置密码邮件里的链接会回落到 Site URL。这正是之前 「验证邮件跳到 localhost:3000」的原因。

3.2 打开 manual linking

Section titled “3.2 打开 manual linking”

进入 Authentication → Providers，在页面上的高级 / 安全设置里打开 Allow manual linking （自托管的对应环境变量是 GOTRUE_SECURITY_MANUAL_LINKING_ENABLED: true）。

不开的话，「账号与安全」页里的绑定与解绑都会被服务端拒绝。这是 Beta 能力，Supabase 的 Dart 客户端里对应 linkIdentity / unlinkIdentity。

3.3 Google provider

Section titled “3.3 Google provider”

Authentication → Providers → Google，填第 4 步拿到的 Client ID 与 Client Secret，保存并启用。

3.4 Apple provider

Section titled “3.4 Apple provider”

Authentication → Providers → Apple：

字段 填什么
Client IDs 第 5 步创建的 Services ID（demo 是 com.yoosee.developer.demo.web）
Secret Key (for OAuth) 用第 5 步的 .p8 生成的客户端密钥

关于 Client IDs 的顺序：只有当你的项目同时使用原生 Sign in with Apple （sign_in_with_apple 插件 + signInWithIdToken）时才需要注意——那种情况下 Services ID 必须排在 第一位，否则网页登录会被 Apple 拒绝，而原生登录仍然正常，属于很难排查的失败。本 demo 只用 网页重定向，Client IDs 里只有 Services ID 一项，顺序无影响。

Supabase Auth 目前不支持 Apple 的 Server-to-Server 通知端点，Apple 侧那个设置留空。

4. Google Cloud Console

Section titled “4. Google Cloud Console”
  1. 建项目（或复用已有项目），在 Google Auth Platform 里配好 Audience（哪些用户可以登录）、Data Access / Scopes、Branding。 Scopes 至少要有 openid、.../auth/userinfo.email、.../auth/userinfo.profile。
  2. Clients → Create client，Application type 选 Web application。
    • Authorized redirect URIs 填 Supabase 的回调地址： https://agvjkfcdnrbdgsbtsldd.supabase.co/auth/v1/callback （在 Supabase 的 Google provider 页面也能直接看到这个值）
    • Authorized JavaScript origins 在纯移动端场景通常可以留空：Google 只要求这两个字段至少 填一个，我们填的是 redirect URI。
  3. 保存 Client ID 与 Client Secret，填进 Supabase 的 Google provider。

不需要建 Android / iOS 类型的客户端，也不需要 Google Play 控制台。Supabase 文档里 名为「Flutter (iOS and Android)」的那一节讲的是原生 google_sign_in + signInWithIdToken 方案（要填包名、SHA-1、Bundle ID），本 demo 不走那条路。

5. Apple Developer

Section titled “5. Apple Developer”

  1. App ID：在 Identifiers 里找到（或新建）App 的 Bundle ID （demo 是 com.yoosee.developer.demo），在 Capabilities 里勾上 Sign in with Apple。

  2. Services ID：在 Identifiers 里新建一个 Services ID （demo 是 com.yoosee.developer.demo.web），然后 Configure：

    • Primary App ID 选上一步的 App ID。
    • Domains and Subdomains 填 agvjkfcdnrbdgsbtsldd.supabase.co。
    • Return URLs 填 https://agvjkfcdnrbdgsbtsldd.supabase.co/auth/v1/callback。

  3. Key：在 Keys 里新建一个启用 Sign in with Apple 的 Key，下载 AuthKey_XXXXXXXXXX.p8 （只能下载一次，丢了要重新生成）。记下 Key ID 与 Team ID。

  4. 生成客户端密钥，填进 Supabase 的 Apple provider 的 Secret Key (for OAuth)。两条路：

    • 推荐：用 Supabase 控制台里提供的工具，填 .p8 / Key ID / Team ID / Services ID 直接生成， 私钥不会离开浏览器。（该工具目前在 Safari 下不可用，换 Chrome 或 Firefox。）

    • 命令行：Apple 的客户端密钥就是一个 ES256 签名的 JWT，可以自己签：

      sub 必须是 Services ID（不是 App ID），aud 固定 https://appleid.apple.com， kid 是 Key ID。生成的密钥应当是三段、约 300 字符，其中第三段恰好 86 字符； 如果第三段是 95 字符左右，说明 DER 没转成 raw，Apple 会拒。

    这个密钥最多只能用 6 个月，Apple 侧硬限制。到期后 Apple 登录会失败，需要重新生成并更新 Supabase 配置——建议在日历里排一个 5 个月的循环提醒。

  5. 在 Services 里为 Sign in with Apple for Email Communication 登记邮件来源域名。 用户选「隐藏我的邮箱」时，Apple 会通过这些域名转发邮件——不登记的话，相关邮件发不出去。

.p8 是私钥，必须放在仓库外。 仓库的 .gitignore 已经忽略 *.p8 与 secret/， 但别把「被忽略」当成「可以放这儿」——一旦误提交（或误传），要立刻去 Apple 开发者后台 吊销这个 Key 并重建，然后重新生成客户端密钥。

6. 两端原生工程

Section titled “6. 两端原生工程”

仓库里已经配好，这里只是让你核对取值（新增平台或改 scheme 时才需要动）：

位置 内容
android/app/src/main/AndroidManifest.xml ① 主 Activity 上的 VIEW / DEFAULT / BROWSABLE intent-filter，scheme=com.yoosee.gwiotflutterdemo、host=auth-callback；② android:launchMode="singleTask"；③ <meta-data android:name="flutter_deeplinking_enabled" android:value="false" />
ios/Runner/Info.plist CFBundleURLTypes，CFBundleURLSchemes = com.yoosee.gwiotflutterdemo
supabase/config.toml 本地开发的 additional_redirect_urls 与 enable_manual_linking

Android 那两项缺一不可，否则表现是「回调到了原生但 Dart 侧毫无反应、界面停在白页」：

  • singleTask：从浏览器回来的 VIEW intent 带 NEW_TASK|CLEAR_TOP。用 Flutter 模板默认的 singleTop 时，系统会新建一个 Activity 实例接走回调，deep link 落到新引擎上，而 supabase_flutter 的 deep link 监听挂在原来那个引擎上，于是永远收不到。
  • flutter_deeplinking_enabled=false：不关的话 Flutter 引擎会自己抢 VIEW intent 去 push 路由， 和 app_links 争同一个 intent。app_links 官方 example 也是这么配的。

Flutter 侧不需要额外加依赖：supabase_flutter 内部已经用 app_links 监听回调，只要 URL 带上 code / access_token / error* 任一参数就会自动换成会话，也不需要手写回调解析。

7. 真机端到端验收

Section titled “7. 真机端到端验收”

每一条都要在真机上跑（模拟器对系统认证窗口与 deep link 的表现与真机不同）。

  1. 邮箱确认回 App：宿主账号模式 → 注册 → 去邮箱点确认链接 → 应当直接回到 App。
  2. 重置密码回 App：忘记密码 → 收邮件 → 点链接 → 应当直接回到 App。
  3. Google 登录：登录页点「使用 Google 登录」→ 系统认证窗口 → 完成后回到 App 并进入主界面。 Android 上 Google 会被 Supabase 强制走外部浏览器，这是预期行为，不是 bug。
  4. Apple 登录：同上。留意 Apple 的「隐藏我的邮箱」——账号邮箱会变成 xxx@privaterelay.appleid.com。
  5. 绑定：「我的 → 账号与安全」→ 给账号绑定另一个提供方 → 完成后列表里应显示已绑定。
  6. 解绑：解绑一个提供方 → 二次确认 → 列表应刷新。
  7. 解绑保护：只剩一种登录方式时，解绑应当被拒绝并给出原因（unlinkIdentity 的服务端规则是 账号至少保留两种登录方式）。
  8. 更换邮箱：「账号与安全 → 更换」→ 填真实邮箱 → 去新邮箱点确认链接 → 回到 App 后账号邮箱 应变成新值，并且客户云映射里的邮箱也一起更新（App 会重新走一次宿主账号登录来刷新映射）。
  9. 邮箱密码登录方式：设置密码 → 退出登录 → 用该邮箱加密码登录应能成功。Apple 隐藏邮箱的 账号在设置密码前应当先被提示去更换邮箱。

8. 安全说明

Section titled “8. 安全说明”

自定义 URL scheme 没有归属验证。 Android 上任何 App 都能声明同名的 scheme 并抢到回调，从而拿到 URL 里的授权码或 token。因此当前配置只适用于 demo 与开发调试。正式产品应当改用验证过的 Android App Links + iOS Universal Links（需要自己在 HTTPS 域名下托管 AASA 文件——Supabase 明确不提供该托管），或者至少在回调到达后校验来源。

另外两条与 Supabase Auth 相关的通用要求：

  • App 与任何前端只能使用 publishable key，service_role 密钥绝不能进客户端。
  • 允许的重定向地址要精确列举，不要用通配符放开，否则会形成开放重定向。

9. 为什么不做「不同邮箱的旧账号合并」

Section titled “9. 为什么不做「不同邮箱的旧账号合并」”

需求里出现过「第三方首次登录时，询问是否有旧邮箱账号需要绑定」。要分清两种情况：

  • 邮箱相同：Supabase 的 Automatic Linking 默认就把同邮箱的第三方身份绑到同一个账号， demo 不需要任何界面。
  • 邮箱不同：需要 manual linking，但时机上走不通——第三方 OAuth 一完成，新账号就已经建好、 第三方身份已经挂在它上面；此时想把这个身份改挂到旧邮箱账号，必须先以旧邮箱账号登录再 linkIdentity，而该身份已被占用会冲突。Supabase 没有合并两个账号的公开 API，唯一解是拿 service_role 先删掉新账号再重新绑定。

不做还有业务原因：合并会换掉 Supabase user id，而云云对接的 unionId 取的就是 user id， accessId 由它推出——用户会发现「登录后设备全没了」。完整

Apple「隐藏邮箱」的问题不走合并，而是同一个账号换一个邮箱（updateUser 传新邮箱并确认）， user id 不变、accessId 不变、设备归属不变。

10. 常见失败与排查

Section titled “10. 常见失败与排查”
现象 多半是
点邮件链接跳到 localhost:3000 或打不开 Supabase 的 Additional Redirect URLs 没加这个 scheme，或 App 侧没登记
日志里有 Attempting to open an URL without a Flutter RootViewController. 可忽略。这是 Flutter 引擎自己的 deep link 处理在找 FlutterViewController，而根控制器被包进了 GWIoTNavigationController（SDK 内置页面跳转要求这么包）。插件侧的 deep link 不受影响——紧跟着的 supabase.supabase_flutter: handle deeplink uri 就是证明
点链接回到 App 但一直没登录 回调 URL 与登记值不一致；或 code 换会话失败，看 onAuthStateChange 的错误流
第三方登录完成回到 App 却停在登录页 provider 没启用，或 Google 的 Authorized redirect URI 与 Supabase 回调地址不一致
绑定/解绑立刻报错 Supabase 的 manual linking 没打开
Apple 网页登录被拒、原生登录正常 Client IDs 里 Services ID 没排第一位（仅同时用原生登录时会遇到）
点登录后白页 / 停在浏览器里回不来 / 报 PlatformException(Error, Error while launching ...) 用了应用内浏览器。确认 hostAuthLaunchMode() 返回 externalApplication
回调回到 App 后提示登录失败，日志里有 SocketException: Read failed ... Connection reset by peer App 进程到 *.supabase.co 的 HTTPS 连接被重置，与 Supabase 配置无关。常见于设备上的代理只覆盖了浏览器没覆盖 App（Safari 里 Google 登录成功、App 直连被重置），把 demo 加进代理规则或换网络重试
用 Apple 登录后邮箱是 @privaterelay.appleid.com 用户选了「隐藏我的邮箱」，属正常；用「账号与安全 → 更换邮箱」换掉
换邮箱后按新邮箱反查不到账号 客户云映射里的邮箱没刷新，检查是否重新走过一次宿主账号登录
